## 一、软件架构设计

### 1.1 主要内容回应

本选题是**闯关解密类桌面游戏**（文本模式 + JavaFX/Swing GUI + 可选 Socket 联机 + H2 存档），并非典型 B/S 电商系统，因此采用**分层架构 + 命令模式**，在合适层次上**对照** Spring Boot / Spring MVC / RESTful / Vue 的设计思想，而非强行将全部业务迁入 Web 栈。

### 1.2 总体架构（四层）

```
┌─────────────────────────────────────────────────────────┐
│  表现层（Presentation）                                   │
│  Parser / JavaFX·Swing GUI / 联机客户端输出               │
├─────────────────────────────────────────────────────────┤
│  应用层（Application）                                    │
│  Game、LevelManager、LevelTimer、CommandWords、Parser     │
├─────────────────────────────────────────────────────────┤
│  领域层（Domain）                                         │
│  Room、Player、Item、TeleportRoom、NPC、LevelConfig       │
├─────────────────────────────────────────────────────────┤
│  基础设施层（Infrastructure）                             │
│  H2 存档、Socket 多人服务端、Maven 构建、GitHub Actions   │
└─────────────────────────────────────────────────────────┘
```

**表现层**负责接收玩家输入、展示房间描述、背包与「距熄灯（23:00）还有 XXX 秒」。文本模式下 `Parser` 读入命令；图形界面（F7）将按钮/输入框映射为同一套命令字符串（例如 `take`/`drop` 弹窗输入物品名；`eat` 一键执行食用背包食物），实现**界面与逻辑分离**，对应 Spring MVC 中 **View** 的职责。

**应用层**中的 `Game` 协调关卡流程；`LevelManager` 管理五关解锁与失败重开；`LevelTimer` 维护熄灯倒计时；各 `XxxCommand` 继承抽象类 `Command`，由 `CommandWords` 注册分发。该结构对应 Spring MVC 的 **Controller + 路由**：命令名即“路径”，`execute(Game)` 即“处理请求”，**不**把业务规则写在 `Game.play()` 的巨型分支里。

**领域层**封装房间拓扑、物品、玩家负重、条件门、黑暗区等规则，对应 Spring 中的 **Service / Domain Model**，与界面、数据库解耦。

**基础设施层**实现 H2 持久化（F8）、多人 Socket 或可选 REST 网关（F6）、CI 打包发布，对应 **Repository / 外部集成**。

### 1.3 与 Spring / Spring Boot / Spring MVC / RESTful / Vue 的对照

| 课程技术 | 本项目实践方式 | 说明 |
|----------|----------------|------|
| **Spring MVC** | 命令模式 + `Game` 调度 | `Command` ≈ Controller；`Room`/`Player` ≈ Model；GUI/控制台 ≈ View |
| **Spring Boot** | Maven 可执行 JAR + 可选联机服务端模块 | 主程序 `Main` 一键启动；联机服务端可独立 `main`，内嵌 Tomcat 非必须 |
| **RESTful API** | F6 联机协议（推荐 JSON over HTTP 或 Socket 文本协议） | 资源示例：`POST /api/game/command`、`GET /api/game/state`；若首版用 Socket，文档中仍按 REST 资源风格设计消息体，便于扩展 Web 大厅 |
| **Vue** | F7 桌面 GUI 为主；**可选** Vue 管理页 | 排行榜/存档查询可用 Vue + REST 只读展示；游戏内操作仍以 JavaFX/Swing 实时交互 |

**架构选型结论：** 对本选题而言，**桌面分层 + 命令模式**是“适当架构”；Spring Boot 适用于**联机大厅、存档 API、统计后台**等可拆子系统；Vue 适用于**运维/数据展示页**。核心玩法（五关、计时、物品）保持在 Java 领域层，避免前后端过度拆分导致联调成本过高。

### 1.4 关键设计决策（段落说明）

房间连接关系在 `Game.createRooms()` 中**一次定义、全局不变**，关卡差异通过 `LevelManager` 解锁出口与刷新物品实现，避免每关重建地图。拓展命令 `use`、`submit`、`combine` 等独立于已实现之 F5 `take`/`drop`，符合开闭原则。熄灯倒计时 `LevelTimer` 为横切关注点，由应用层统一扣减，表现层只读显示秒数。H2 仅持久化关卡号、剩余秒数、通关记录，不序列化整个对象图，降低基础设施层复杂度。

## 二、小组软件过程与项目管理

### 2.1 主要内容回应

本组基于 **DevOps 思想**，使用 **GitHub** 作为统一项目管理平台，覆盖需求（Issue）、文档（`docs/`）、代码（仓库）、自动化流水线（Actions）与发布（`master` + JAR 制品）。不单独搭建 Jira，以降低课程项目运维成本，但**过程活动与 DevOps 闭环一致**：计划 → 分支开发 → PR → 评审 → CI → 合并 → 发布。

### 2.2 软件过程阶段划分

| 阶段 | 时间 | 目标 | 主要产出 |
|------|------|------|----------|
| **立项与策划** | 6/1 — 6/3 | 定选题、五关流程、功能 F/E 编号 | [会议记录.md](会议记录.md) |
| **迭代一：框架** | 6/1 — 6/7 | E9/E10/E11、拓展命令雏形、第 1—2 关 | `feature/xmq`、`feature/lj` |

## 三、软件分支管理

### 3.1 主要内容回应

本组采用**精简分支策略**：长期仅 **`master`（发布）** 与 **`dev`（集成）**；辅助分支**最多四类**——个人开发（`feature/姓名拼音`）、文档、debug、冲突解决，**禁止**每人另开 `feature/gui` 等多个功能分支。课程演示版本以 **`master` 标签 + Actions 制品** 为准；发布前由组长从 `dev` 打 tag（如 `v1.0.0`）。

### 3.2 分支模型说明

| 分支类型 | 命名 | 用途 | 谁可合并 |
|----------|------|------|----------|
| **主分支** | `master` | 答辩稳定版 | 仅组长：`dev` → `master` |
| **集成分支** | `dev` | 全部验收代码汇入 | 组员 PR，组长 Review |
| **个人开发** | `feature/xmq` `feature/lj` `feature/phx` `feature/pqj` | 每人固定一个 `feature/xxx`，写代码与修 Bug | 本人 PR → `dev` |
| **文档** | `feature/docs` | 会议记录、README、实践说明等 | PR → `dev` |
| **debug** | `debug` | 临时调试、试验性改动 | 验证后 PR → `dev` 或丢弃 |
| **冲突解决** | `merge/conflict` | 仅处理 `dev` 合并冲突 | 解决后 PR → `dev`，**立即删除** |

**原则：** 不为 GUI、多人、单关卡等分别建长期分支；Bug 修复在个人分支完成。历史遗留的 `feature/*` 合并进 `dev` 后应删除。

### 3.3 标准工作流（段落）

组员每日先 `git pull origin dev`，再 `git merge dev` 进自己的 `feature/xxx` 个人分支开发。功能或修复完成后，本地 `mvn checkstyle:check`、`mvn test` 通过，推送并 PR 至 `dev`。文档改动在 `feature/docs` 分支提交后同样 PR 至 `dev`。组长或同伴 Review、CI 绿灯后合并；个人分支**保留**但须经常同步 `dev`。发布周组长发起 `dev` → `master` PR，从 Actions 取 `game-jar` 答辩。

### 3.4 代码冲突与解决

冲突热点：`Game.java`、`CommandWords.java`、`pom.xml` 等。预防：按模块分文件、每日 `merge dev`、小步提交。一旦出现多人改同一文件，由当事人从最新 `dev` 拉出 **`merge/conflict`** 分支，手动解决 `<<<<<<<` 标记，跑通 `mvn test` 后 PR 合并，**禁止** `push --force` 到 `dev`/`master`。合并完成后删除 `merge/conflict` 并在 PR 中列出冲突文件与验证步骤。

## 四、软件代码评审

### 4.1 主要内容回应

本组将代码评审作为 **合并 `dev` 的必经环节**，以 **GitHub Pull Request 同行评审（Peer Review）** 为主，关键模块（计时器、关卡切换、联机同步）由组长与另一组员**结对过读（Pair Review）**，不替代个人自测与 CI。

### 4.2 评审类型与适用场景

| 类型 | 本组做法 | 适用 |
|------|----------|------|
| **同行评审（Code Review）** | 每个 PR 至少 1 人 Approve（组长或模块负责人） | `feature/*`、`debug`、`merge/conflict` → `dev` |
| **结对编程 / 结对评审** | 肖梦琪 + 刘晶联调命令与 `LevelManager`；彭慧星 + 肖梦琪对接 F6 协议 | 架构热点、接口变更 |
| **自检清单** | PR 模板：Checkstyle、JUnit、手动场景、是否影响熄灯计时 | 提交者填写 |

### 4.3 评审关注点

评审不仅看格式，更看：**是否破坏 F1—F5 已有行为**；拓展命令是否在 `CommandWords` 正确注册；`LevelTimer` 扣秒是否与 GUI 一致；H2 读写是否覆盖异常；多人命令是否破坏服务端权威状态。评论需具体（文件 + 行 + 建议），作者修改后回复或 push 新 commit，直至 Approve。

### 4.4 工具与记录

- **工具：** GitHub PR「Files changed」、行内评论、Review summary。  
- **规范：** [CONTRIBUTING.md](../CONTRIBUTING.md) 提交信息须写清 `feat:` / `fix:` 描述。  
- **模板：** [.github/PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md) 强制自查项。

## 五、持续集成与部署

### 5.1 主要内容回应

本组在 **GitHub Actions** 上实现 **持续集成（CI）**：推送 `dev`、`feature/**`、`debug`、`merge/**` 或向 `master`/`dev` 提 PR 时自动执行规范检查、单元测试与打包，产出可执行 JAR。**持续部署（CD）** 限于课程场景：制品上传至 Actions Artifacts，答辩现场下载运行；不强制上云容器生产部署，但保留 Docker 扩展说明。

### 5.2 CI 流水线（`.github/workflows/maven.yml`）

流水线名称 **CI Pipeline**，主要步骤如下：

1. **Checkout** 拉取代码  
2. **Set up JDK 11**（Temurin，Maven 缓存）  
3. **Checkstyle** — `mvn checkstyle:check`（validate 阶段规范门禁）  
4. **单元测试** — `mvn test`（JUnit 5，Surefire 报告上传）  
5. **构建打包** — `mvn package -DskipTests=false`  
6. **上传制品** — `*-jar-with-dependencies.jar` 至 Artifact `game-jar`  
7. **上传测试报告** — `target/surefire-reports/`  

任一 step 失败则 PR **不可合并**（建议开启分支保护规则）。

### 5.3 自动化测试策略

| 层次 | 工具 | 范围 |
|------|------|------|
| 静态规范 | Checkstyle | 全源码 + 测试代码 |
| 单元测试 | JUnit 5 | `RoomTest`、命令类、计时与关卡逻辑（持续补充） |
| 集成/手动 | 组内试玩清单 | 五关通关、熄灯失败、submit 错物、读档 |

本地门禁与 CI 一致：`mvn checkstyle:check` → `mvn test` → `mvn package`。

### 5.4 打包与发布

- **构建命令：** `mvn clean package`  
- **运行：** `java -jar target/world-of-zuul-1.0.0-SNAPSHOT-jar-with-dependencies.jar`  
- **发布：** 组长将 `dev` 合并至 `master` 后，从 Actions 下载 `game-jar` 或本地 `mvn package` 产物，附于实训报告与 B 站演示。  
- **版本标识：** 建议在 `master` 打 Git tag `v1.0.0` 与报告版本一致。  

### 5.5 容器管理与运行（课程扩展说明）

当前首版以 **JAR 直跑** 为主。若联机服务端需隔离环境，可选用 **Docker** 多阶段构建：阶段一 `maven:3.8-eclipse-temurin-11` 编译，阶段二 `eclipse-temurin:11-jre` 仅包含 JAR 与 H2 数据卷挂载路径。容器非本阶段必交付项，写入报告体现对「容器管理与运行」的理解即可。

示例 `Dockerfile` 思路（伪代码，按需添加至仓库）：

```dockerfile
FROM maven:3.8-eclipse-temurin-11 AS build
WORKDIR /app
COPY . .
RUN mvn -q package -DskipTests=false

FROM eclipse-temurin:11-jre
WORKDIR /app
COPY --from=build /app/target/*-jar-with-dependencies.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```
