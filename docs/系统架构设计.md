## 1. 引言

### 1.1 编写目的

本文档描述《熄灯前归寝》的系统总体架构、前后端划分、技术选型及关键设计决策，供开发、测试与实训答辩使用。

### 1.2 项目背景

本作是基于 World of Zuul 扩展的**闯关解密类桌面游戏**：玩家从校门出发，在五关限时内集齐物品、完成解密，最终回寝室执行 `sleep` 通关。游戏具有**高频命令交互、复杂状态、实时倒计时**等特点。

### 1.3 架构选型结论

本项目采用 **混合架构（Hybrid Architecture）**：

| 组成部分 | 技术 | 职责 |
|----------|------|------|
| 游戏内核 | Java 四层 + 命令模式 | 五关规则、计时、地图、命令（不依赖 Spring） |
| 服务后端 | Spring Boot + Spring MVC + RESTful API | 存档、联机、通关记录、排行榜 API |
| 主前端 | Swing + 文本 Parser | 主玩法交互（F7） |
| 辅前端 | Vue 3 + Axios | 排行榜、存档查询、联机大厅 |
| 持久化 | H2 | 存档槽、通关记录 |

**不采用**纯 B/S 架构（Vue 整游戏 + Spring Boot），原因见第 2 节。

## 2. 架构选型分析

### 2.1 候选方案对比

| 方案 | 描述 | 结论 |
|------|------|------|
| 纯 B/S | Vue SPA 做游戏 UI，所有操作走 REST | ❌ 不适合：每步 go/take/use 产生 HTTP 延迟；需重写整套游戏 UI |
| 纯桌面 | 仅 Java Swing + H2，无 Spring/Vue | ⚠️ 玩法可行，但课程 Spring/Vue 应用体现不足 |
| **混合架构** | Java 内核 + Spring REST 服务 + Swing 主客户端 + Vue 辅前端 | ✅ **采用** |

### 2.2 选型依据

1. 游戏操作为**命令驱动**，单机应进程内直接调用，不走网络。
2. 联机（F6）需要**服务端权威状态**，适合 Spring Boot 提供 REST 接口。
3. 存档与统计（F8）适合 **Repository + REST**，供 Swing 与 Vue 共用。
4. Vue 适合**只读/轻量写**的 Web 页，不适合替代 Swing 做实时闯关操作。

## 3. 系统总体架构

### 图 1　系统总体架构（混合架构）

![图1 系统总体架构](images/fig1-overall.png)

*图 1：客户端层 → 游戏内核 → Spring Boot 服务 → H2 数据库*

系统自上而下分为四层部署视图：

```
客户端层（Swing 主前端 + Vue 辅前端）
        ↓ 本地调用 / HTTP REST
游戏内核（Java 四层 + 命令模式）
        ↓ 联机与存档场景
服务后端（Spring Boot + Spring MVC + REST）
        ↓
H2 数据库
```

### 3.1 客户端层

| 组件 | 技术 | 说明 |
|------|------|------|
| 主前端 | Swing、`Parser` | 房间、背包、命令、距熄灯倒计时；F7 必做 |
| 辅前端 | Vue 3、Vue Router、Pinia、Axios | 排行榜、存档列表、联机大厅；体现课程 Vue |

### 3.2 游戏内核

单机与联机**共用**同一套规则代码，包路径 `cn.edu.whut.sept.zuul`，**不引入 Spring 依赖**。

### 图 2　游戏内核四层架构

![图2 游戏内核四层架构](images/fig2-core-layers.png)

*图 2：表现层 / 应用层 / 领域层 / 基础设施*

| 层 | 主要类 |
|----|--------|
| 表现层 | `Parser`、`gui/GameWindow`、GUI 绑定层 |
| 应用层 | `Game`、`LevelManager`、`LevelTimer`、`CommandManager` |
| 领域层 | `Room`、`Player`、`Item`、`NPC`、`LevelConfig`、`TeleportRoom` |
| 基础设施 | `infrastructure.persistence`（单机 H2 DAO） |

### 3.3 服务后端

包路径 `cn.edu.whut.sept.zuul.infrastructure.server`，独立 `ServerApplication` 启动。

### 图 3　Spring Boot 服务后端三层

![图3 Spring Boot 服务后端三层](images/fig3-spring-layers.png)

*图 3：Controller → Service → Repository*

| 层 | 职责 | 示例 |
|----|------|------|
| Controller | REST 入口 | `@RestController` |
| Service | 业务编排 | `GameEngineFacade`、`MultiplayerSessionService` |
| Repository | 数据访问 | `SaveRepository`、`ClearRecordRepository` |

`GameEngineFacade` 内部调用内核 `CommandManager`，**不在 Spring 层重复实现五关规则**。

### 3.4 持久化层

H2 嵌入式数据库，**仅存储摘要字段**：

- 当前关卡号、剩余秒数、玩家昵称（存档）
- 通关关卡、通关时间（记录）

不序列化完整 `Game` 对象图。

## 4. 前后端架构

### 图 4　前后端职责划分

![图4 前后端职责划分](images/fig4-frontend-backend.png)

*图 4：Swing 主前端负责玩法，Vue 辅前端负责数据展示*

### 4.1 主前端（Swing）— 游戏客户端

- **单机模式**：Swing → `CommandManager.executeCommand()` → 内核，**不经 HTTP**。
- **联机模式**：Swing → `POST /api/game/command` → Spring 服务端 → `GameEngineFacade` → 内核。
- 职责：五关主玩法、实时倒计时、背包与房间展示。

### 4.2 辅前端（Vue）— Web 数据门户

- Vue → `GET /api/leaderboard`、`/api/records` 等 REST 接口。
- 职责：排行榜、通关记录、存档列表、联机房间列表。
- **不承担** `go`、`take`、`use` 等高频游戏操作。

### 4.3 服务后端（Spring Boot）— API 服务

- 提供 RESTful JSON 接口，内嵌 Tomcat，默认端口 `8080`。
- 联机场景下持有**权威** `Game` 实例与 `LevelTimer`，计时以服务端为准。

## 6. RESTful API 设计

| 方法 | 路径 | 说明 | 调用方 |
|------|------|------|--------|
| GET | `/api/saves/{id}` | 读档 | Swing / Vue |
| POST | `/api/saves` | 存档 | Swing |
| GET | `/api/records` | 通关记录 | Vue |
| GET | `/api/leaderboard` | 排行榜 | Vue |
| POST | `/api/rooms` | 创建联机房间 | Swing / Vue |
| POST | `/api/rooms/{id}/join` | 加入房间 | Swing |
| POST | `/api/game/command` | 执行命令（联机） | Swing |
| GET | `/api/game/state` | 获取游戏状态 | Swing |

**统一响应格式：**

```json
{
  "code": 0,
  "data": {
    "level": 2,
    "remainingSeconds": 187,
    "roomDescription": "博学北楼二楼转角…"
  },
  "message": "ok"
}
```

## 7. 课程技术应用映射

| 课程技术 | 是否采用 | 工程位置 |
|----------|----------|----------|
| Spring | ✅ | `infrastructure.server`：IoC、事务 |
| Spring Boot | ✅ | `ServerApplication`，内嵌 Tomcat |
| Spring MVC | ✅ | `@RestController`，REST 接口层 |
| RESTful API | ✅ | `/api/*`；单机命令不走 REST |
| Vue | ✅ | `vue-portal/` 辅前端 |
| 分层 + 命令模式 | ✅ | 游戏内核 |

**内核内的 MVC 对照：** `Command` ≈ Controller，`Room`/`Player` ≈ Model，Swing ≈ View。

## 9. 关键设计决策

1. **地图一次构建**：`Game.createRooms()` 定义十房固定拓扑；关卡差异由 `LevelManager` 控制出口与物品刷新。
2. **命令模式扩展**：`use`、`submit`、`combine` 等独立成类并注册，符合开闭原则。
3. **计时横切**：`LevelTimer` 统一管理「距熄灯（23:00）还有 XXX 秒」；联机以 Spring 服务端为准。
4. **规则单一来源**：Spring 通过 `GameEngineFacade` 调用 `CommandManager`，避免 Web 层重复业务逻辑。
5. **轻量存档**：H2 仅存关卡号、剩余秒数、通关记录，读档时由 `LevelManager` 重建状态。
6. **前端职责分离**：Swing 玩游戏，Vue 看数据。
